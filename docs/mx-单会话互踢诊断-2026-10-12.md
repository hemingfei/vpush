# MX 单会话互踢诊断与平台迁移记录（2026-10-12）

> 背景：平台域名迁至 `https://mx.2026.foodtop1.com/` 后，生产 WS「经常被踢下线、
> 重连也失败」。本文记录诊断过程、根因结论与代码修复；复现工具为
> `scripts/mx_ws_probe.py`。

## 一、平台侧变更（浏览器 ground truth，Playwright addInitScript 钩子实测）

| 项 | 旧（naaifu.cn，≤2026-10-09） | 新（foodtop1.com） |
|---|---|---|
| 登录/业务域 | `mx.2026.naaifu.cn` | `mx.2026.foodtop1.com`（旧域 `/business-api/*` 已 404，仅剩静态页） |
| business-api 版本 | `/business-api/5` | `/business-api/4`（登录响应 `hosturl="/4"`，前端拼成 `/business-api/4`） |
| WS 端点 | `{api_base}/socket.io/` | `wss://mx.2026.foodtop1.com/business-api/4/socket.io/?EIO=4&transport=websocket`（形态不变，版本段变） |
| namespace / 认证帧 | `/msg`；`40/msg,{"tt":…,"token":…,"version":"web"}` | 不变（紧凑 JSON） |
| 心跳 | engine.io v4：服务端 25s 发 `2`，客户端回 `3` | 不变（pingInterval=25s / pingTimeout=20s） |
| cookie | 无 | 无 |

## 二、根因：同账号单 WS 会话互踢（新平台行为）

A/B 实验（同 token、同网络、先后两个连接）时间戳铁证：

```
984681.45  [连接#1 curlffi] ws_open           ← 连接 #1 建立并站住
984725.17  [连接#2 prod]   ws_open            ← 43.5 秒后连接 #2 握手完成
984725.18  [连接#1] 收到 41/msg,              ← 仅 ~6ms 后，服务端向 #1 发 Socket.IO DISCONNECT
（此后 #1 再无任何帧：无心跳、无 WS close——僵尸静默，10 分钟以上）
```

结论：**新连接接入后，服务端毫秒级踢掉同 token 的旧连接，且踢后静默不发 close**。
连 python-socketio 的 aiohttp 传输也要等 engine.io 读超时（pingInterval+pingTimeout
=45s）才判定断开。

### 与既有指纹防护的关系

- 三种客户端人格（生产 python-socketio+aiohttp、curl_cffi impersonate chrome146、
  手写最小 EIO 客户端+aiohttp）在本地家宽 IP 下**全部正常存活**——平台没有在 WS
  握手上做 TLS/头指纹检测，既有的 curl_cffi impersonate（HTTP）+ 浏览器形态握手头
  （WS）防护仍然有效且够用。
- 「经常被踢」不是指纹暴露，而是**账号本人开网页端**（或其他客户端接入）触发互踢。

### 旧生产的故障链（「重连也失败」）

1. 用户开网页 → vpush WS 被 `41` 踢（僵尸静默，最长 45s 后才感知断开）；
2. 旧策略 16-36s 后立即重连 → 踢掉网页端 → 网页 socket.io-js 无限自动重连
   （1-5s 内回来）→ 再踢 vpush；
3. vpush 重连没站住 60s 宽限 → **永久放弃自动重连**，只能人工接入；
4. 若配置仍指向旧域 naaifu.cn → 重连握手直接 404，必失败。

## 三、代码修复（本次提交）

1. **`app/fetchers/mx/ws.py`：双路径重连策略**
   - 连接动作本身失败（网络错/端点 404）：保留旧语义——16-36s 随机重连一次，再失败放弃；
   - **连上后被断**（含 41 踢、僵尸静默超时、网络中断）：改走**阶梯退避**
     `KICK_BACKOFF_LEVELS = 2-3 / 5-7 / 10-15 分钟随机`——给对方（通常是账号本人
     开着网页）留出结束会话的时间，避免互踢战；连接站住（≥60s）即归零；三档
     耗尽才放弃并告警（告警文案提示关闭网页会话）。
2. **域名/版本默认值**：`app/config.py` MxConfig 默认 `foodtop1.com/business-api/4`；
   `scripts/mx_login.py` 同步，且 `business_base_of()` 正确处理新版 hosturl 路径形态
   （`"/4"`、`"/business-api/4"`、旧版完整域名三种）。
3. **图片下载 Referer**：`app/avatar_cache.py` MX 分支改为多域名匹配
   （`naaifu.cn`/`foodtop1.com`）+ Referer 按图片自身 host 派生，域名再轮转免改。

既有部署的 config.yaml 里存的旧域名由换 token 流程自愈（b7e1a7c 后）：
`mx_login.py --write api` 探针前先读生产实例实际存的 api_base（新增
`fetch_current_mx_api_base`，走 VPUSH_URL 管理 API），生产基址探不通时按登录
hosturl 切换并把新 api_base/ws_url 随 token 一并写回——平台再换域名，下一次
换 token 即自动纠正，无需手工改后台。

## 四、诊断工具：scripts/mx_ws_probe.py

```
python scripts/mx_ws_probe.py                    # 登录（验证码走视觉模型）+ 三变体各 120s
python scripts/mx_ws_probe.py --token <t>        # 跳过登录
python scripts/mx_ws_probe.py --duration 45 --repeat 3
python scripts/mx_ws_probe.py --watch curlffi    # 单变体长跑监控
python scripts/mx_ws_probe.py --ws-url wss://…/socket.io/   # 端点覆盖
```

- 三变体：`prod`（生产原类直跑）/ `curlffi`（Chrome TLS 指纹 + 手写 EIO 客户端）/
  `aiohttp`（同手写客户端、Python TLS——与 curlffi 只差 TLS 指纹，用于隔离变量）；
- 验证码识别复用 `scripts/mx_login.py` 的 `ai_ocr`（`MX_VISION_*` 或 `LLM_*` 指向
  Ark 多模态，与 Jenkins mx-token 任务同源）；凭据走根目录 `.env` 的
  `MX_ACCOUNT`/`MX_PASSWORD`；
- 事件明细落盘 `.scratch/mx_ws_probe.jsonl`（含 mono 时间戳，便于互踢时序分析）。

判读：`prod` 被踢而 `curlffi` 存活 → WS 握手指纹检测（本次未观察到）；两连接
先建者收到 `41` → 单会话互踢；全部存活 → 平台间歇性问题，用 `--watch` 长跑。

## 五、运维建议

1. **账号分离（治本）**：vpush 用独立 MX 账号挂 WS，本人浏览用另一账号——
   单会话互踢天然免疫。当前测试账号即适合此用途。
2. 不要在挂 WS 的账号上长期开网页端：新策略下 vpush 会退避等待并在网页关闭后
   自愈（约 2-15 分钟内恢复），但网页一直开着就占着会话。
3. 平台域名/版本可能再变：先跑 `mx_ws_probe.py` 看自动发现结果，或浏览器 F12
   看 `localStorage.mx_web_hosturl`（新版本形态记录在登录响应 `hosturl`）。
