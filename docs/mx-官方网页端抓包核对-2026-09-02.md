# MX 官方网页端抓包核对报告（2026-09-02）

> 方法：真实账号人工登录（账号/密码/图形验证码均人工输入），Chrome 152.0.7977.76 / Windows 10 x64。
> Playwright 记录全部 HTTP 请求；请求头取自 CDP `Network.requestWillBeSentExtraInfo`（wire 级真实发送头）；
> WebSocket 双向帧逐帧记录。本文逐项核对 `mx-防风控优化措施.md` 第六节「抓包核对清单」。
> 文中 token 已脱敏。

## 一、清单逐项结论

| 清单项 | 结论 |
|---|---|
| ① WS 是 polling→upgrade 还是直连 | **websocket 直连**：URL 带 `?EIO=4&transport=websocket`，服务器 open 包 `"upgrades":[]`。`ws.py` 的 `transports=["websocket"]` 与官方一致，注释「与网页端一致」成立 |
| ② 连上后是否 emit 事件 | **不 emit 任何业务事件**。只有命名空间握手 `40/msg,{tt,token,version:"web"}`，之后纯收：服务器推 `42/msg,["room_msg","<LZ+AES密文>"]`、心跳服务器发 `2` 客户端答 `3`。「只听不说」与官方一致，无需补进房/已读事件 |
| ③ HTTP 是否带 sign 签名 | **不存在**。认证仅 `token` 请求头（`/master-api/api/notice` 等 GET 把 token 放 query）。请求体是明文业务字段 `{rid,msgid,pagesize,tt}` 等。无需逆向（此项按文档约定不逆向，实测也无需逆向） |
| ④ 头形态与常量是否一致 | **有出入**，见第三节差异表（`accept`、`ad`、`i`、`priority`） |
| ⑤ 官方端 UA 形态 | 网页端 = 桌面 Chrome（本次实测 Windows 10 / Chrome 152；`sec-ch-ua` 三件套同版本）。会话内未观察到移动端形态 |

## 二、官方端实测画像

### 2.1 冷启动/刷新时序

1. `POST /master-api/api/login`（登录前：`GET /master-api/api/code?tt=` 图形验证码）
2. `POST /master-api/api/user/info` → `POST /master-api/api/system/config`
3. `POST /business-api/5/api/room/list`，body `{"pages":1,"limit":1000000,"tt":...}` —— **官方一次全量拉房间列表**
4. `POST /business-api/5/api/msg/tip`，body `{"tt":...}`（全局未读提示）
5. `POST /master-api/api/room/grouplist`（房间分组）
6. 恢复上次打开的房间：`POST /business-api/5/api/room/view` + `/api/msg/list` + `/api/room/notice`
7. `GET /master-api/api/notice?tt=...&token=...`（200）；官方同时试了 `GET /business-api/5/api/notice?...`（404，官方自己也在试错）
8. `POST /master-api/api/user/issign`、`/api/user/showad`、`/member-ai-api/api/ai-analysis/member/modules`（AI 功能）
9. WS 连接（见 2.3）

**每次点开房间 = `room/view` + `msg/list` + `room/notice` 三连**，`msg/list` body 为
`{"rid":16125,"msgid":0,"pagesize":30,"tt":...}`，**pagesize=30**，单次请求不深翻。

`room/view` body：`{"rid":16125,"tt":...}` —— 进房/观看上报。

### 2.2 业务 POST 的完整 wire 头（`room/view`、`msg/list` 实测，HTTP/2）

```http
:authority: mx.2026.naaifu.cn
:method: POST
:path: /business-api/5/api/msg/list
:scheme: https
accept: */*
accept-encoding: gzip, deflate, br, zstd
accept-language: zh-CN,zh;q=0.9
ad: true
content-length: 56
content-type: application/json
i: qq
origin: https://mx.2026.naaifu.cn
priority: u=1, i
referer: https://mx.2026.naaifu.cn/
sec-ch-ua: "Chromium";v="152", "Not?A_Brand";v="24", "Google Chrome";v="152"
sec-ch-ua-mobile: ?0
sec-ch-ua-platform: "Windows"
sec-fetch-dest: empty
sec-fetch-mode: cors
sec-fetch-site: same-origin
token: <redacted>
user-agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/152.0.0.0 Safari/537.36
version: web
```

要点：

- **无 cookie**，认证只有 `token` 头（`version: web` 常驻）
- **`accept: */*`** —— 不是 axios 默认的 `application/json, text/plain, */*`（`client.py` 的 `XHR_ACCEPT` 与官方不符）
- **`ad: true`、`i: qq`** 是官方前端常驻自定义头，登录请求也带（本账号实测值如此）
- `origin` 同源 POST 也发送（vpush 发 Origin 是对的），`referer` 为站点根
- `priority: u=1, i`（Chrome 116+ 的 H2 priority 头；curl_cffi 模板是否自动带需用线上人格实测确认）
- `accept-language: zh-CN,zh;q=0.9` 与 vpush `ACCEPT_LANGUAGE` 逐字节一致
- `sec-fetch-*` 三件套与 vpush 现值一致

### 2.3 WS 会话实测

```
→ 连接 wss://mx.2026.naaifu.cn/business-api/5/socket.io/?EIO=4&transport=websocket
← 0{"sid":"...","upgrades":[],"pingInterval":25000,"pingTimeout":20000,"maxPayload":1000000}
→ 40/msg,{"tt":1788335616771,"token":"<redacted>","version":"web"}
← 40/msg,{"sid":"..."}
← 42/msg,["room_msg","ႎ䅄ˀ㰘삦Ґ...（LZ+AES 密文，解密后即消息 JSON）"]
← 2        （服务器 ping）
→ 3        （客户端 pong）
```

- 命名空间 `/msg`、auth 载荷 `{tt, token, version:"web"}` 与 vpush 完全同形
- 心跳方向：**服务器发 `2`、客户端答 `3`**，间隔 25s/超时 20s（engine.io v4 标准行为，python-socketio 自动处理，无差异）
- 客户端全程不 emit 业务事件
- **URL 路径在 `/business-api/5/socket.io/` 下**；vpush 按 `config.example.yaml` 配置连的是
  `wss://host/msg` + path `/socket.io` → `wss://host/msg/socket.io/`，形态不同（服务器两者都接受，
  但对风控日志而言这是可区分的路径特征）
- 一个观察：**登录后当次会话没有连 WS，冷启动/刷新才连**（疑似只在应用启动时建立连接）

## 三、vpush 现实现差异清单（按优先级）

| # | 差异 | vpush 现状（实测代码） | 官方实测 | 建议 |
|---|------|----------------------|---------|------|
| 1 | `accept` 头 | `application/json, text/plain, */*` | `*/*` | `client.py` 的 `XHR_ACCEPT` 改为 `"*/*"` |
| 2 | 缺 `ad` / `i` 头 | 不发送 | `ad: true`、`i: qq` 常驻（含登录请求） | `_headers()` 补 `"ad": "true"`、`"i": "qq"`。**已用第二个账号复核：登录前的验证码请求就已携带这两个头，两账号值一致 —— 确认为前端内置常量，与账号/注册渠道无关，可放心硬编码** |
| 3 | WS URL 形态 | `wss://host/msg` + `/socket.io` | `wss://host/business-api/5/socket.io/` | `ws_url` 改 `wss://mx.2026.naaifu.cn/business-api/5`（`ws_path` 保持 `/socket.io`） |
| 4 | room/list 形态 | 100/页逐页，最多 50 页 | **一次 `{"pages":1,"limit":1000000}`** | 恢复官方单次全量：既与官方形态一致，又把每次同步从最多 50 个请求降到 1 个。原「limit=1000000 是机器人实锤」的判断被实测推翻——该参数官方自己就发，频率才是信号。保留既有 2-6 小时随机同步节奏不变 |
| 5 | msg/list pagesize | 50 | 30 | `page_size` 默认改 30 |
| 6 | UA/平台人格 | macOS Chrome 146（curl_cffi chrome146 模板） | Windows Chrome 152 | 暂不改：curl_cffi 0.16.0 最高仅 chrome146 模板（已核实），chrome146 已是库上限；现值 UA/sec-ch-ua/JA3 内部自洽。待 curl_cffi 出更高版本模板再整体升级 |
| 7 | 进房上报 | 兜底/手动拉取只调 `msg/list` | 每次看房先 `room/view {rid,tt}` | 可选：拉取某房间前先发一次 `room/view`，更接近「人打开了房间」的行为链；收益存疑（vpush 本就低频），自行决策 |
| 8 | 心跳 | python-socketio 自动处理 | 服务器 ping/客户端 pong | 无需改动，行为一致 |

落地注意：改动 1/2 需同步更新 `tests/test_mx.py` 的人格契约测试（`XHR_ACCEPT`、wire 头断言）；
改动 3 需同步 `config.example.yaml`、`app/config.py` 默认值与文档；改动 4 需调整 `get_rooms`
相关测试口径。——以上已全部落地，见第六节。

## 七、补充发现：房间点选与历史消息的本地缓存模型（2026-09-02 晚补测）

实测方式：真实点选对照（新房间 → 切回旧房间 → 再点回）+ localStorage 检查 + 点击「加载更早」。

- 每次点选房间**必发的只有** `room/view`（进房/已读上报）+ `room/notice`（房间公告；
  公告弹窗有 sessionStorage 按日已读标记），**不会重新拉取历史消息**——连第一次点开
  本会话未打开过的房间也是如此。
- 历史消息按房间持久化在 **localStorage**：键名 `mx_web_messages_<rid>`（实测缓存约
  35 个房间，单房 2KB~40KB）。点选时直接本地渲染；新消息由 WS `room_msg` 实时追加
  进缓存——WS 本来就推送全部订阅房间，所以每个房间的近期消息客户端都在攒。
- `msg/list` 只在两种场景出现：
  1. **冷启动补漏**：对「上次打开的房间」拉一次 `{"rid":..,"msgid":0,"pagesize":30}`，
     与本地缓存合并，补上页面关闭期间的消息；
  2. **向上翻页**：房间内点「加载更早」→ `{"rid":..,"msgid":<本地最旧消息id>,"pagesize":30}`，
     以本地最旧消息为游标分页回拉。
- localStorage 其他键：`mx_web_token`（token 持久化，即「关窗重开自动登录」的载体）、
  `mx_web_userinfo`、`mx_web_login_account`、`mx_web_dark_mode`、`mx_web_room_group_order`、
  广告已读标记（`mx_web_ad_*_YYYY-MM-DD_n`）等。

**对 vpush 的印证**：vpush 的数据库即官方「localStorage 缓存」的等价物（同键去重），
WS 全房间实时推送与官方客户端同构，开窗时的一次 `msg/list(msgid=0)` 恰好等价于官方
冷启动对恢复房间的补漏——行为模型一致，无需再调整。

## 四、对既有文档的修正

- `ws.py` 注释「仅使用 websocket，与网页端一致」—— ✅ 实测成立
- 「`limit=1000000` 单条日志就是机器人实锤」—— ❌ 被实测推翻，官方每次冷启动就是这么发；有罪的是**频率与节拍**，不是这个参数
